\title{A Small Verifier That Learns From Outcomes:\\
\large Judging coding-agent runs locally with Gemma~4, and separating issue difficulty from run quality}
\author{John Soliva\\\small D1A project, \url{https://github.com/jonpol01/d1a}}
\date{DRAFT --- \today}

\maketitle

\begin{abstract}
A coding agent cannot see the hidden tests that decide whether its patch resolves an issue. A verifier that estimates
$P(\text{resolved})$ can pick among several runs, filter runs for training, and learn from outcomes as they arrive.
We study a small one: D1A-E4B (Gemma~4 E4B, a LoRA adapter and a pointer head), which reads the issue, the agent's patch and the end of its run,
and answers in one forward pass in a median 1.5\,s on a laptop.
Our central observation is that the usual metric hides what matters. On 921 public agent runs from 83 unseen repositories,
\emph{knowing how other runs of the same issue fared} already scores AUROC 0.958, so global AUROC mostly measures issue difficulty.
Ranking runs \emph{of the same issue} (within-issue AUROC) is the harder test, and on it no scorer we tried is clearly better than another: on 119 test issues
with mixed outcomes, cheap trajectory heuristics reach 0.622, D1A 0.616 zero-shot and 0.642 after a 2.5-hour LoRA on a laptop
($+0.020$ over the heuristics, 95\% CI $[-0.053, +0.093]$).
The same confound inflates learned verifiers evaluated on random splits of runs: on 32{,}340 runs, a text verifier scores AUROC 0.946 under a random split
and 0.736 on unseen repositories, and its within-issue AUROC falls from 0.643 to 0.493.
Finally, D1A learns from outcomes through a loop that recalibrates, retrains and promotes a candidate only through a statistical gate;
over three rounds of 300 outcomes, recalibration cut the calibration error from 0.068 to 0.017--0.036, while no retrained candidate was clearly better and
the gate kept the current model every time.
All data is public and all code is open.
\end{abstract}

\section{Introduction}
LLM coding agents edit repositories in long runs of tool calls and then submit a patch, without knowing whether the hidden tests will pass.
This is the setting of the Gemma~4 Developer Agent challenge, where an agent runs offline on a fixed Gemma~4 model under a time budget per task:
a small verifier on the same hardware is what such an agent can afford to consult.
A verifier's value lies in decisions \emph{about a given issue}: which of several runs to submit, which runs to keep as training data, when to try again.
These decisions compare runs of the same issue, yet verifiers are usually evaluated by global AUROC over runs of many issues, which also rewards
recognising which issues are easy.

Verifiers for coding agents already exist (Section~\ref{sec:related}); we do not claim a new kind of verifier. Our contributions are:
\begin{enumerate}
\item \textbf{Separating issue difficulty from run quality.} On held-out repositories, an issue prior alone reaches global AUROC 0.958. We report
within-issue AUROC next to global AUROC and find that within issues a small decision model and cheap heuristics are indistinguishable (Section~\ref{sec:verifier}).
\item \textbf{Split leakage, measured.} On the same runs, random-run splits let a learned verifier score by recognising issues; grouping by issue removes
the inflation (Section~\ref{sec:leakage}).
\item \textbf{A local verifier that learns from outcomes}, with a statistical promotion gate, released as a library (\texttt{d1a.feedback})
(Section~\ref{sec:loop}).
\end{enumerate}

\section{Related Work}\label{sec:related}
\paragraph{Verifiers for software-engineering agents.} SWE-Gym trains verifiers on agent trajectories and uses them for inference-time scaling, selecting
among sampled trajectories~\cite{swegym}. SWE-RM is a 30B execution-free reward model that treats classification accuracy and calibration as crucial for
reinforcement learning~\cite{swerm}. Agentic Rubrics derive contextual rubrics as a verification signal~\cite{rubrics}. Closest to us, a rubric-supervised critic is learned from sparse
real-world outcomes, jointly predicting 24 behavioural rubrics and success, and improves best-of-8 reranking over random on the ``rerankable'' subset of
trajectories~\cite{critic}; restricting evaluation to issues with mixed outcomes is thus established. What we add is the decomposition itself: how much of
pooled AUROC an issue prior explains, how heuristics and a small decision model differ within issues, and how random splits inflate learned verifiers.

\paragraph{Early failure prediction.} FailFast-RestartSmart trains a 0.6B monitor on trajectory prefixes and restarts runs predicted to fail~\cite{failfast};
EarlyEval predicts outcomes early with gradient-boosted classifiers~\cite{earlyeval}. Our anytime experiment is a weaker instance of this idea and is
reported as a contrast.

\paragraph{Self-improvement with gates.} Audited skill-graph self-improvement promotes a candidate only after verifier-backed replay~\cite{asgsi}, and
self-authored verification is shown to be unreliable, motivating an external acceptance gate~\cite{seal}. Verification also has to keep up with the policy it
judges~\cite{horizon}. Our gate is external in the same sense, driven by real outcomes, and decides with a bootstrap interval over repositories.

\section{The Verifier}\label{sec:verifier}
\paragraph{Model.} D1A~\cite{d1a} is a decision model built on Kev~\cite{kev}: a causal LM backbone with a LoRA adapter runs one prefill over a document and
typed questions under a block-causal mask, and a pointer head scores each option against the question's decision token. The backbone is Gemma~4 E4B.
D1A-E4B v0.4, released before this work, was trained on general decisions and pull-request labelling, never on agent runs.

\paragraph{Input.} The document holds the issue (up to 3{,}000 characters), the agent's final patch (up to 6{,}000) and the last steps of its run
(up to 3{,}000; each step up to 800). The question asks whether the patch correctly fixes the issue, so that the repository's tests for it would pass.
Inputs are 1.5k tokens at the median and 5.5k at most.

\paragraph{Data.} nebius/SWE-agent-trajectories (CC-BY-4.0) holds 80{,}036 SWE-agent runs on 3{,}591 issues, each with \texttt{target}
(resolved by the hidden tests), the trajectory and the patch; the test logs are never read. Repositories are assigned to train (70\%), dev (10\%) and test (20\%)
by a hash of the name. We prepared 2{,}000 training runs from 377 repositories (at most four per issue, successes first); dev holds 1{,}142 runs and test
921 runs from 83 repositories (up to 8 per issue; 12.4\% resolved; 23 of 123 test issues have both outcomes).

\paragraph{Training and calibration.} One LoRA run continues D1A-E4B v0.4 for 100 optimizer steps of 8 runs (800 of the prepared runs; learning rate
$5\cdot10^{-5}$), 2.5\,h on an Apple M1 Max at no cost. Platt scaling on the logit is fitted on dev only. The heuristics baseline is a logistic regression over six
trajectory features (patch size, a clean ``submitted'' exit, number of steps, error observations, printed success, test-file edits), fitted on training-split runs.
The ``+ heuristics'' combinations refit the heuristic weights jointly with D1A's logit on dev; refitting the heuristics alone on dev does not improve them.

\paragraph{Issue difficulty dominates global AUROC.} Most issues are resolved by all or none of their runs, so a scorer that recognises the issue ranks runs
well globally without judging any run. Within issues the picture changes (Table~\ref{tab:verifier}): on our 23 mixed test issues the heuristics reach 0.536, D1A 0.617 zero-shot and 0.661 after training.
Those 23 issues are too few: on 119 mixed-outcome issues from the test repositories of all 80{,}036 runs (952 runs, up to 8 per issue, each issue keeping at least
one success and one failure), the gap closes (Table~\ref{tab:within}). Within issues, a 4B-class decision model reading the issue, the patch and the end of the run
does not judge runs better than six trajectory features.

\paragraph{Picking one of several runs.} Picking one of 8 recorded runs per issue (97 issues, 23 with mixed outcomes; bootstrap over issues), compared with a random pick
(14.7\% resolved): zero-shot D1A $+5.9$ points $[+2.2, +10.2]$, heuristics + r1 $+4.9\,[+0.5, +9.3]$, r1 alone $+2.8\,[-1.0, +6.6]$, heuristics
$-1.3\,[-5.0, +2.7]$; an oracle reaches 26.8\%. At $k=2$ and $k=4$ the gains are smaller and not significant. Training did not improve selection over the
zero-shot model here.

\paragraph{Filtering training data.} Keeping the 10\% of test runs that r1 trusts most gives 40.2\% truly resolved runs (37), against 22.8\% for the
heuristics (21), 19.6\% for the agent's own clean exit and 15.2\% at random.

\paragraph{Calibration, honestly.} After recalibration all scorers are reasonably calibrated, and the heuristics are best (ECE 0.019). No scorer is
confident enough to decide ``submit or keep working'' on its own: the highest precision any threshold reaches with at least 10 runs submitted is 41\% for r1
(9.0\% of runs) and 65\% for heuristics + r1 (1.8\% of runs). We therefore recommend the probability for comparing runs and filtering data, not as a
stand-alone stop signal.

\paragraph{Anytime verification is weak.} Scoring an unfinished run at its tenth action (patch absent, final exit hidden), the heuristics fall below chance
(AUROC 0.40) and zero-shot D1A reaches 0.66, which is $+0.16$ over chance. Replaying stop-and-restart policies on recorded runs under an action budget, the
verifier gains at most 1.3 points (12.8\% vs 11.5\% for never stopping at a 90-action budget; oracle 15.9\%), far less than FailFast-RestartSmart reports
with a dedicated prefix monitor~\cite{failfast}.

\paragraph{Latency.} Median 1.48\,s and p95 2.79\,s per run (MLX, 8-bit, M1 Max).

\section{Split Leakage}\label{sec:leakage}
The issue-difficulty confound also inflates learned verifiers when runs of one issue fall on both sides of a split. We measure this on the same runs under three
5-fold protocols (random runs; grouped by issue; grouped by repository) with four verifiers refitted per fold: an issue prior from the training folds (pure
leakage by construction), the heuristics, a TF-IDF model of the issue and patch text, and both together.

\caption{Out-of-fold AUROC under three 5-fold splits of the same 32{,}340 runs (3{,}591 issues, 1{,}276 repositories, at most 10 runs per issue, 10.6\% resolved;

(95\% CI, bootstrap over repositories): text $+0.210\,[+0.192, +0.229]$, heuristics + text $+0.158\,[+0.144, +0.174]$, heuristics $+0.005\,[+0.001, +0.009]$;
by issue: text $+0.013\,[-0.004, +0.027]$, heuristics + text $+0.005\,[-0.006, +0.016]$.}\label{tab:leakage}

Under a random split the text model's global AUROC is 0.946, yet its within-issue AUROC falls to 0.493: when issues leak, it learns to recognise them \emph{instead of} judging runs, and loses the within-issue discrimination it has when issues cannot leak (0.643).
Grouping by issue removes the inflation, and grouping by repository adds little beyond that in this data. Evaluations of learned verifiers should group by issue
at least, and report within-issue discrimination. We have not checked whether any published verifier result used a random split.

\section{Learning From Outcomes}\label{sec:loop}
\texttt{d1a.feedback} logs each decision with the model version that made it, records the outcome when it arrives, and improves the model in three steps,
cheapest first: (1) an outcome calibrator refits each yes/no probability on the outcomes (Platt scaling~\cite{platt}, which also corrects a shifted base rate);
(2) a small LoRA update trains on the resolved decisions; (3) a promotion gate replaces the current model only if the candidate's held-out log loss is lower
with a 95\% bootstrap interval over repositories entirely below zero, and no frozen evaluation suite regressed by more than one point.

\paragraph{Rounds.} Starting from r1, batches of 300 unseen runs arrive with their outcomes. Each round, 80\% of the batch (by repository) becomes training
records and 20\% a calibration slice; each model is recalibrated only on slices it never trained on; the gate decides on dev repositories; the served model is
measured on test repositories.

\begin{table}[h]\centering\small
\begin{tabular}{lcccl}\toprule
Round & outcomes & test AUROC & test ECE & gate \\\midrule
0 (r1, no feedback) & 0 & 0.808 & 0.068 & -- \\
1 & 300 & 0.808 & 0.036 & rejected: log loss $+0.026\,[+0.016, +0.058]$ \\
2 & 600 & 0.808 & 0.017 & rejected: $+0.010\,[-0.004, +0.050]$ \\
3 & 900 & 0.808 & 0.031 & rejected: $-0.007\,[-0.016, +0.014]$ \\\bottomrule
\end{tabular}
\caption{The served verifier after each round on test repositories (four runs per issue). Recalibration on the held-out calibration slices (77, 147 and 210
outcomes) cut the calibration error; the retrained candidates (30 steps each on the 223, 453 and 690 training records so far) were worse (round 1) or not clearly better (rounds 2--3),
and the gate kept the current model, so the served AUROC did not change.}\label{tab:rounds}
\end{table}

Three rejections do not show that retraining cannot help, only that 30-step updates on a few hundred outcomes did not, and that the gate stops what is not
clearly better. The gate's power is limited by the dev set (about 7\% resolved): only a sizable log-loss improvement can clear a 95\% interval. Larger outcome
batches, several candidate settings per round, and a measured minimum detectable effect are the next steps.

improves~\cite{horizon}. \pending{Gemma-4-31B agent runs from the challenge (repeated runs per task): within-issue AUROC and calibration after

\section{Limitations}
One agent family (SWE-agent with Llama models) carries the results so far; the Gemma~4 agent study is pending. Only 23 test issues have mixed outcomes, so
within-issue and best-of-$k$ estimates are noisy. The verifier sees truncated inputs. The challenge provides per-repository code graphs and embeddings; this
verifier does not use them, because it judges a finished run from its issue, patch and trajectory, and in a separate study of ours a D1A localiser over the
provided graphs did not beat BM25 at finding the code to change. Under 5-fold cross-validation on a separate sample of 600 runs, zero-shot D1A appeared to add
$+0.069$ global AUROC to the heuristics; on the fixed test split it added nothing ($-0.003$). Both were grouped by repository, so this is a gain that did not
replicate, not leakage.
